Case study — Cairn

Engineering an honest job‑search engine

Job boards are full of ghost postings, and the tools built on top of them are full of AI slop. I built Cairn — a job-search engine whose core feature is that it refuses to lie to you — and then refactored it from a zero-test script into a dual-backend, multi-tenant system without changing a single output byte.

01 01 The itch

Constraints first, features second

A meaningful fraction of job postings are ghosts — roles that are expired, filled, or were never real. The tools that grew up around this market mostly made it worse: scrapers that violate the terms of every site they touch, LLMs ghost-writing cover letters recruiters have learned to detect on sight, auto-apply bots that spray a thousand applications and land in spam filters.

Cairn started from the stances, not the features.

  • No scraping — every source is a legal, public API.
  • No AI ghost-writing — outreach drafts are deterministic templates with [brackets] a human fills in; no LLM writes a word of your text.
  • No auto-apply, ever.
  • Statuses move only when you move them — a background scan can discover a new role, but nothing in the system will ever silently advance your application from interested to applied.

These read like product copy, but each one is an engineering constraint with teeth, and most of them ended up enforced in code or schema rather than in a style guide. That enforcement is what the rest of this page is about. The codebase is a private repo — what follows is the architecture, honestly told, including the parts that aren't finished.

02 02 The pipeline

Anatomy of a scan

"Zero results" and "your API key is dead" are very different facts, and a tool that conflates them is lying by omission. The scan is built around that distinction. It is one function with six stages: fetch → dedupe → lazy-enrich → score → filter/rank → persist. Company mode hits the employer's own ATS board (applicant tracking system — the Greenhouse- or Lever-style job board a company runs itself) directly, through Greenhouse, Lever, Ashby, and SmartRecruiters adapters — all keyless public APIs — plus aggregators filtered to that employer. Search mode goes keyword-first across the aggregators.

The organizing idea is fail-soft. Every adapter catches its own failures and returns an empty list plus a health string — a scan never crashes because one source did. The health strings are blunt by design: ok: 4 roles, skipped: no key, error: rate-limited / quota exceeded (HTTP 429), no public ATS board matched this name. The UI shows them all, always.

Two smaller decisions I like: description fetches for sources whose list endpoints don't include them are lazy and bounded — only title-relevant roles trigger a per-posting call, so a 500-role board doesn't become 500 HTTP requests. And the company-mode employer filter requires the query's normalized tokens as whole-token subsets of the employer name, so a scan for "Box" doesn't drag in "Boxed" while "Match Group LLC" still matches "Match Group".

03 03 Provenance

Dedupe with a paper trail

The same role shows up on the company's ATS board and on two aggregators, with different URLs, different descriptions, and sometimes a different employer string. Most tools pick one copy arbitrarily. Cairn collapses them into one row but keeps the receipts: every source that saw the role stays in a sources list, shown as chips in the UI.

The merge rules encode a worldview. The direct ATS link always wins — if an aggregator copy arrives first and the ATS copy arrives second, the ATS row takes over as canonical and inherits the accumulated source trail. The longer description wins. A known posted date backfills a missing one. The result is that you always apply at the employer's own board, never through an aggregator redirect — and a role visible on both the company ATS and an aggregator is itself a signal that the req is real and active, surfaced rather than discarded.

The golden-master suite — snapshot tests that pin the engine's entire JSON output byte-for-byte against committed fixtures — locks this in: one fixture role arrives via both Greenhouse and an aggregator, and the test asserts the merged row carries both source chips while the apply URL is the greenhouse.io one. Provenance isn't a nice-to-have here; it's the product's answer to ghost postings.

04 04 Scoring

A score that shows its work

Every scoring product in this category produces an opaque number that users reasonably mistrust. Cairn's score is a plain weighted blend of five components, collapsing to a tier — Strong, Good, or Stretch:

  • Title match — damped hard when the title doesn't match at all, rather than dropped.
  • Skills coverage — core skills weighted more heavily.
  • Seniority fit — hard mismatches are dropped outright before scoring.
  • Location fit
  • Domain relevance

Two properties matter more than the formula. First, it's explainable by construction: the components that produced the number are the same data shown to the user — matched skills as chips, and a "gaps" list computed by diffing the job description's tech vocabulary against the profile's skills, so you see exactly which keywords your resume is missing for this specific role. No embedding, no model, nothing that can't be read in an afternoon.

Second, it's honest about what it isn't. The UI says so in as many words: the score is a profile-fit estimate, not a callback prediction. A deterministic rubric can be audited, versioned, and argued with. A vibe from a model can't. For a tool whose brand is trust, that tradeoff wasn't close — and the profile itself is data, a JSON document in a profiles row, so the rubric's inputs are per-user without the engine changing shape.

05 05 Structural promises

History you can't rewrite

The funnel event log is append-only. Every status transition writes a job_status_events row — old status, new status, actor, timestamp — and nothing in the codebase updates or deletes one. The reason to land this table early is unforgiving: history can never be backfilled. Analytics, follow-up queues, and outcome calibration can all be built later, but only on events that were actually recorded at the time.

Rescans upsert fresh postings data while your statuses survive untouched — there's a test whose whole job is proving that a re-scan doesn't reset interested back to new. The promise from section 01 — statuses move only when you move them — is carried by the event log and its tests, not by anyone remembering to be careful.

06 06 The seam

One seam, two databases — and a tenancy gate that runs on both

Cross-tenant leakage is the one bug class that kills a trust-positioned product, so it's the one class with a standing gate. The setup that gate protects: Cairn is built as a local single-user edition on SQLite and a pooled cloud edition on Postgres — same codebase, selected by DATABASE_URL. The port is deliberately small: nothing outside a single store module knows which backend is running. Instead of SQLAlchemy (rejected in writing — see the ADR rejection table below), the adapter is about forty lines of psycopg glue: ? placeholders rewritten to %s, dict-style rows, commit-on-clean-exit. Each backend keeps its own migration history and version number, because Postgres arrived after the big schema split and has no legacy to carry.

The schema itself is four tables with one ownership chain: users → profiles → matches ← postings. Postings are shared facts; matches are one profile's relationship to a posting — score, tier, gaps, status. The split exists because multi-tenancy makes a combined row wrong by construction: two profiles matching the same posting cannot share a status column.

Tenancy is enforced at a chokepoint: every per-profile store function requires a profile_id — there is no unscoped variant to call by accident, and web handlers never touch tables directly. And because a tenancy property that only holds on the dev database is not a property, the cross-tenant isolation suite is parametrized across SQLite × Postgres and runs as a permanent CI gate, with a postgres:17 service container in every CI run.

The same seam enforces a privacy promise outright. The cloud database has no contacts table. Cairn's referrals engine matches your exported LinkedIn connections CSV against hiring companies — third-party PII, the most radioactive data in the system. The promise is "your contacts file never touches our servers," and rather than enforce it with a code path someone could regress, the Postgres schema simply does not define a connections table. The /api/connections/* endpoints check the backend and return 403 before touching the engine. On the cloud backend there is nothing to write to, no query to forget a WHERE clause on, no backup that could leak it. The database cannot hold what the product promised not to hold. That's my favorite line of architecture in the project, and it's a schema omission.

07 07 The discipline

Refactoring a zero-test codebase behind golden masters

Cairn began life as a working script with zero tests — and a refactor queue that included a package split, an app factory, a four-table schema migration, and a second database backend. The rule I set before touching any of it: tests before refactors, golden masters green before and after.

The golden-master suite runs the entire engine — adapters through persistence — against recorded fixtures, then compares the full JSON output to a committed snapshot, byte for byte. One hard-won detail: the fixtures generate posting dates relative to today, and the first snapshots recorded them absolutely — so the goldens silently expired the day after recording, going red on identical engine output. The fix normalizes dates to TODAY-N placeholders, making the snapshots stable regardless of when the suite runs. Characterization tests (tests that pin current behavior rather than intended behavior) have failure modes of their own; this one taught me to test the test.

The payoff was the schema split: migrating one jobs table into users/profiles/postings/matches while list_matches kept returning the joined row under the exact old keys. The frontend was untouched and the goldens stayed byte-identical through the entire migration.

The other half of the discipline is six ADRs — architecture decision records, one-page write-ups of each decision and its reasoning — including a standing rejection table where microservices, Kubernetes, SQLAlchemy, and CRDT sync engines are turned down in writing, each with a reason and a revisit trigger. Rejections that aren't written down get re-litigated forever; these stay rejected until load, not fashion, says otherwise. CI runs the lot — lint, types, and all ~100 tests on Python 3.11 and 3.12, isolation gate on both backends.

08 08 Status

What it is today, and what it is not yet

Today Cairn is a working single-user system, end to end.

  • Scan any company with a public ATS board.
  • Get explainably scored, deduped results with full provenance.
  • Track a funnel whose history is append-only.
  • Draft outreach from templates no AI wrote.
  • Keep a scheduled watchlist that reports failures instead of hiding them — and never moves a status on its own.

The dual-backend store is verified against a real Postgres 17 with the app booted end-to-end on it. Runtime dependencies: Flask and requests, pinned. That's the whole list.

What it is not yet: a cloud product you can sign up for. Authentication isn't built — the session plumbing has exactly one function to replace when it lands, which was the point of building the seam first. Self-serve export and delete are designed (the FK cascade chain already makes delete a one-statement operation) but the endpoints aren't written. There's no hosted deployment and no email infrastructure.

The honest version of the pitch is that the hard architectural promises — isolation gated in CI, privacy enforced by schema, history that can't be rewritten — were built before the first user, because they're the kind of thing you can't retrofit credibly. The rest is work, and it's written down.
